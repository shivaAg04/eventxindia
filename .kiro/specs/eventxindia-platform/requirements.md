# Requirements Document

## Introduction

EventXIndia V1 is a Flutter and Firebase application that digitizes an offline event staffing process. The platform serves three roles within a single application that uses role-based navigation: Students apply for events, Vendors create and manage events, and Admins approve vendors and monitor platform activity. The system uses Firebase Authentication (Phone OTP), Cloud Firestore, Firebase Storage, and Firebase Cloud Messaging.

Version 1 explicitly excludes wallet, withdrawals, payment gateway, chat, trust score, discipline score, QR attendance, and AI verification. Earnings are estimated only, with no real payments.

## Glossary

- **System**: The EventXIndia application, comprising the Flutter client and Firebase backend services.
- **Auth_Service**: The component responsible for phone-based one-time-password authentication, backed by Firebase Authentication.
- **Student**: A user role that applies for and works at events.
- **Vendor**: A user role that creates and manages events and reviews applicants. A Vendor has an approval status of Pending, Approved, or Rejected.
- **Admin**: A user role that approves Vendors and monitors platform activity.
- **Event**: A staffing opportunity created by a Vendor, with a status of Active, Closed, or Completed.
- **Application**: A record of a Student requesting to work an Event, with a status of Pending, Approved, or Rejected.
- **Attendance_Record**: A record storing a Student's check-in time, check-out time, and working hours for an Event.
- **Start_Code**: A code generated by a Vendor that a Student enters to check in to an Event.
- **End_Code**: A code generated by a Vendor that a Student enters to check out of an Event.
- **GPS_Validation**: Verification that a Student's device location is within an acceptable distance of an Event location at check-in.
- **Estimated_Earnings**: A monetary total accumulated for a Student based on completed attendance, with no real payment processing.
- **Pay_Per_Head**: The monetary amount a Vendor offers to pay each Student for working an Event.
- **Report**: A record submitted by a Student or Vendor describing an issue for Admin review.
- **Notification**: A push message delivered through Firebase Cloud Messaging.
- **Student_Profile**: The stored profile data for a Student, including Full Name, Phone Number, Gender, Date of Birth, City, Height, and Profile Photo.
- **Vendor_Profile**: The stored profile data for a Vendor, including Full Name, Agency Name, Phone Number, City, and Address, plus optional Aadhaar/PAN, Website, and Social Links.
- **OTP**: A one-time password sent to a phone number for authentication.

## Requirements

### Requirement 1: Student Authentication and Profile Registration

**User Story:** As a Student, I want to register and log in using phone OTP, so that I can securely access the platform and apply for events.

#### Acceptance Criteria

1. WHEN a Student submits a phone number for login, THE Auth_Service SHALL send an OTP to that phone number that remains valid for 300 seconds after delivery.
2. WHEN a Student submits an OTP that matches the issued OTP within 300 seconds of its delivery, THE Auth_Service SHALL authenticate the Student and grant access to the Student role.
3. IF a Student submits an OTP that does not match the issued OTP or is submitted more than 300 seconds after delivery, THEN THE Auth_Service SHALL reject the authentication attempt, retain the unauthenticated state, and return an error message indicating that the OTP is invalid or expired.
4. IF a Student submits 5 consecutive invalid OTPs for the same phone number, THEN THE Auth_Service SHALL block further OTP attempts for that phone number for 900 seconds and return an error message indicating the phone number is temporarily locked.
5. IF a Student submits a phone number that is empty or does not match the required format of a country code followed by a 10-digit national number, THEN THE Auth_Service SHALL reject the request and return an error message indicating the phone number is invalid.
6. WHEN a new Student completes authentication, THE System SHALL require the following non-empty Student_Profile fields before granting access to the Student Dashboard: Full Name (1 to 100 characters), Phone Number, Gender, Date of Birth (a date in the past), City (1 to 100 characters), Height (50 to 250 cm), and Profile Photo.
7. IF a new Student submits a registration form with any required Student_Profile field missing or outside its specified bounds, THEN THE System SHALL reject the submission and return an error message identifying each missing or invalid field, and SHALL retain the previously entered values.
8. IF a Student uploads a Profile Photo that exceeds 5 MB or is not in JPEG or PNG format, THEN THE System SHALL reject the upload and return an error message indicating the file size or format is invalid.
9. WHEN a Student uploads a Profile Photo that is 5 MB or smaller and is in JPEG or PNG format, THE System SHALL store the photo in Firebase Storage and associate the stored reference with the Student_Profile.

### Requirement 2: Vendor Authentication, Registration, and Approval Status

**User Story:** As a Vendor, I want to register and log in using phone OTP, so that I can create and manage events after approval.

#### Acceptance Criteria

1. WHEN a Vendor submits a 10-digit phone number for login, THE Auth_Service SHALL generate a 6-digit numeric OTP and send it to that phone number within 30 seconds.
2. IF a Vendor submits a phone number that is not exactly 10 numeric digits, THEN THE Auth_Service SHALL reject the request and return an error indication identifying the phone number as invalid, without generating an OTP.
3. WHEN a Vendor submits an OTP that matches the most recently generated OTP for that phone number and is submitted within 300 seconds of generation, THE Auth_Service SHALL authenticate the Vendor and grant access to the Vendor role.
4. IF a Vendor submits an OTP that does not match the generated OTP or is submitted more than 300 seconds after generation, THEN THE Auth_Service SHALL reject the authentication, return an error indication that the OTP is invalid or expired, and allow up to 5 OTP submission attempts per generated OTP.
5. IF a Vendor exceeds 5 failed OTP submission attempts for a single generated OTP, THEN THE Auth_Service SHALL invalidate that OTP and require the Vendor to request a new OTP before further attempts.
6. WHEN a new Vendor completes authentication, THE System SHALL require non-empty values for the Full Name (1 to 100 characters), Agency Name (1 to 150 characters), Phone Number (exactly 10 numeric digits), City (1 to 100 characters), and Address (1 to 250 characters) fields before creating the Vendor_Profile.
7. WHERE a Vendor provides Aadhaar/PAN, Website, or Social Links, THE System SHALL store the provided optional values in the Vendor_Profile.
8. IF a new Vendor submits a registration form with any required Vendor_Profile field missing, empty, or outside its specified length bounds, THEN THE System SHALL reject the submission, retain the entered values, and return an error indication identifying each non-conforming field.
9. WHEN a Vendor_Profile is created, THE System SHALL set the Vendor approval status to Pending.
10. WHILE a Vendor approval status is Pending or Rejected, THE System SHALL prevent the Vendor from creating Events and return an error indication that creation requires Approved status.

### Requirement 3: Role-Based Navigation

**User Story:** As a user, I want the application to present the screens for my role, so that I only see the features relevant to me.

#### Acceptance Criteria

1. WHEN an authenticated user opens the application, THE System SHALL display, within 2 seconds, only the navigation destinations associated with the user's single assigned role of Student, Vendor, or Admin, and SHALL hide all navigation destinations associated with the other two roles.
2. IF a user attempts to access a feature that is not associated with the user's assigned role, THEN THE System SHALL prevent the feature from loading, SHALL display a message indicating the user is not authorized to access that feature, and SHALL return the user to the role's default navigation destination without altering the user's session or data.
3. IF an authenticated user has no assigned role or an unrecognized role value, THEN THE System SHALL deny access to all role-specific features, SHALL display a message indicating that no valid role is assigned, and SHALL not display navigation destinations for any of the Student, Vendor, or Admin roles.
4. IF an unauthenticated user attempts to open the application, THEN THE System SHALL deny access to all role-based navigation and SHALL redirect the user to the authentication screen.

### Requirement 4: Student Dashboard

**User Story:** As a Student, I want a dashboard summarizing my activity, so that I can track my events, attendance, and earnings.

#### Acceptance Criteria

1. WHEN a Student opens the Student Dashboard, THE System SHALL display the list of Events with status Active, or an indication that no Active Events exist when the list is empty.
2. WHEN a Student opens the Student Dashboard, THE System SHALL display the list of Events for which the Student has submitted an Application, or an indication that no such Events exist when the list is empty.
3. WHEN a Student opens the Student Dashboard, THE System SHALL display the list of Events for which the Student's Application status is Approved, or an indication that no such Events exist when the list is empty.
4. WHEN a Student opens Attendance History, THE System SHALL display each of the Student's Attendance_Records showing check-in time, check-out time, and working hours, or an indication that no Attendance_Records exist when none are present.
5. WHEN a Student opens the Student Dashboard, THE System SHALL display the Student's Estimated_Earnings total, displaying a value of zero when the Student has no completed Attendance_Records.
6. WHEN a Student opens Profile, THE System SHALL display the Student_Profile data, including Full Name, Phone Number, Gender, Date of Birth, City, Height, and Profile Photo.
7. IF retrieval of any Student Dashboard data fails, THEN THE System SHALL display an error message indicating the data could not be loaded and SHALL leave the Student's stored data unchanged.

### Requirement 5: Vendor Dashboard

**User Story:** As an approved Vendor, I want a dashboard to manage events and applicants, so that I can staff my events.

#### Acceptance Criteria

1. WHILE a Vendor approval status is Approved, THE System SHALL allow the Vendor to create an Event.
2. WHEN an approved Vendor opens Manage Events, THE System SHALL display the Events created by that Vendor, or an empty-list indication when the Vendor has created no Events.
3. WHEN an approved Vendor opens the applicant list for an Event created by that Vendor, THE System SHALL display the Applications submitted for that Event, or an empty-list indication when no Applications exist.
4. WHEN an approved Vendor approves an Application whose status is Pending for an Event created by that Vendor, THE System SHALL set that Application status to Approved.
5. WHEN an approved Vendor rejects an Application whose status is Pending for an Event created by that Vendor, THE System SHALL set that Application status to Rejected.
6. WHEN an approved Vendor requests an attendance code for an Event created by that Vendor, THE System SHALL generate a Start_Code or End_Code as requested and associate it with that Event.
7. WHEN an approved Vendor opens the attendance view for an Event created by that Vendor, THE System SHALL display the Attendance_Records for that Event, or an empty-list indication when none exist.
8. IF an approved Vendor attempts to approve or reject an Application whose status is not Pending, THEN THE System SHALL retain the existing Application status and return an error indication that the Application is not in a Pending state.
9. IF an approved Vendor attempts to access the applicant list, attendance view, or attendance code generation for an Event not created by that Vendor, THEN THE System SHALL deny the action and return an error indication that the Vendor is not authorized for that Event.

### Requirement 6: Admin Dashboard and Vendor Approval

**User Story:** As an Admin, I want to approve vendors and monitor platform activity, so that I can maintain platform quality.

#### Acceptance Criteria

1. WHEN an Admin approves a Vendor whose approval status is Pending, THE System SHALL set that Vendor approval status to Approved.
2. WHEN an Admin rejects a Vendor whose approval status is Pending, THE System SHALL set that Vendor approval status to Rejected.
3. IF an Admin attempts to approve or reject a Vendor whose approval status is not Pending, THEN THE System SHALL retain the existing approval status and display an error message indicating that the Vendor is not in a Pending state.
4. WHEN an Admin opens the student list, THE System SHALL display all registered Students.
5. WHEN an Admin opens the vendor list, THE System SHALL display all registered Vendors, each with its approval status of Pending, Approved, or Rejected.
6. WHEN an Admin opens the event list, THE System SHALL display all Events, each with its status of Active, Closed, or Completed.
7. WHEN an Admin opens the dashboard metrics, THE System SHALL display the Total Students count as the number of registered Students, the Total Vendors count as the number of registered Vendors, the Active Events count as the number of Events with status Active, and the Completed Events count as the number of Events with status Completed, where each count is an integer of 0 or greater.
8. WHEN an Admin opens the reports view, THE System SHALL display all submitted Reports.
9. IF a requested student list, vendor list, event list, or reports view contains no records, THEN THE System SHALL display an empty-state indication conveying that no records are available.

### Requirement 7: Event Management

**User Story:** As an approved Vendor, I want to create and manage events with full details, so that Students can find and apply for them.

#### Acceptance Criteria

1. WHEN an approved Vendor creates an Event, THE System SHALL require the following non-empty fields: Title (1 to 100 characters), Description (1 to 2000 characters), Date, Start Time, End Time, Location (1 to 200 characters), Slots (integer from 1 to 10,000), and Pay_Per_Head (decimal from 0.01 to 9,999,999.99).
2. IF an approved Vendor submits an Event creation form with any required Event field missing or empty, THEN THE System SHALL reject the submission, retain all entered field values, and display an error message identifying each missing field.
3. IF an approved Vendor submits an Event creation form where the Date is not a current or future calendar date, OR the End Time is not later than the Start Time, OR Slots is outside the range 1 to 10,000, OR Pay_Per_Head is outside the range 0.01 to 9,999,999.99, THEN THE System SHALL reject the submission, retain all entered field values, and display an error message identifying each invalid field.
4. WHEN an Event creation form passes all field-presence and value-range validations, THE System SHALL set the Event status to Active.
5. WHEN an approved Vendor changes an Event status, THE System SHALL set the Event status to exactly one of Active, Closed, or Completed as selected, and SHALL reject any other value with an error message indicating the status is invalid.
6. WHEN an Event passes validation, THE System SHALL store the created Event in the events collection in Cloud Firestore.

### Requirement 8: Event Discovery

**User Story:** As a Student, I want to discover and view events, so that I can decide which events to apply for.

#### Acceptance Criteria

1. WHEN a Student opens event discovery, THE System SHALL display all Events with status Active regardless of the number of remaining Slots.
2. IF no Events have status Active when a Student opens event discovery, THEN THE System SHALL display an empty-state indication that no Active Events are available.
3. WHEN a Student submits a search query of 1 to 100 characters, THE System SHALL display the Events with status Active whose Title or Location contains the query text, ignoring letter case.
4. IF no Active Events match a submitted search query, THEN THE System SHALL display a no-results indication.
5. WHEN a Student selects an Event, THE System SHALL display the Event's Title, Description, Date, Start Time, End Time, Location, Slots, and Pay_Per_Head.
6. WHEN a Student applies to an Event whose status is Active, THE System SHALL create an Application with status Pending and display a confirmation indication that the Application was submitted.
7. IF a Student applies to an Event whose status is not Active, THEN THE System SHALL reject the Application, return an error message indicating the Event is unavailable, and create no Application record.

### Requirement 9: Applications

**User Story:** As a Student, I want to apply to events and have vendors review my applications, so that I can be selected to work.

#### Acceptance Criteria

1. WHEN a Student applies to an Event, THE System SHALL create an Application associated with that Student and that Event and set the Application status to Pending.
2. IF a Student applies to an Event for which an Application from that same Student for that same Event already exists, THEN THE System SHALL reject the duplicate Application, leave the existing Application unchanged, and return an error indication that a duplicate application for the same Event is not allowed.
3. WHEN the Vendor that created the Event approves an Application whose status is Pending, THE System SHALL set the Application status to Approved.
4. WHEN the Vendor that created the Event rejects an Application whose status is Pending, THE System SHALL set the Application status to Rejected.
5. IF a Vendor attempts to approve or reject an Application whose status is not Pending, THEN THE System SHALL reject the action, leave the Application status unchanged, and return an error indication that the Application is not in a Pending state.
6. THE System SHALL store each Application in the applications collection in Cloud Firestore.

### Requirement 10: Attendance Check-In and Check-Out

**User Story:** As a Student, I want to check in and out of events using vendor codes with location validation, so that my working hours are recorded accurately.

#### Acceptance Criteria

1. WHEN a Student submits a Start_Code that matches the Event's generated Start_Code AND GPS_Validation confirms the Student's device location is within 100 meters of the Event Location, THE System SHALL record the check-in time as a timestamp in the Attendance_Record.
2. IF a Student submits a Start_Code that does not match the Event's generated Start_Code, THEN THE System SHALL reject the check-in, retain any existing Attendance_Record unchanged, and return an error message indicating the Start_Code is invalid.
3. IF a Student submits a matching Start_Code while the Student's device location is more than 100 meters from the Event Location, THEN THE System SHALL reject the check-in, retain any existing Attendance_Record unchanged, and return an error message indicating that location validation failed.
4. IF a Student submits a matching Start_Code but the device location cannot be obtained within 30 seconds, THEN THE System SHALL reject the check-in, retain any existing Attendance_Record unchanged, and return an error message indicating that the device location is unavailable.
5. IF a Student submits a Start_Code for an Event in which a check-in time is already recorded for that Student, THEN THE System SHALL reject the check-in, retain the existing Attendance_Record unchanged, and return an error message indicating the Student is already checked in.
6. WHEN a Student submits an End_Code that matches the Event's generated End_Code AND a check-in time is already recorded for that Student, THE System SHALL record the check-out time as a timestamp in the Attendance_Record.
7. IF a Student submits an End_Code that does not match the Event's generated End_Code, THEN THE System SHALL reject the check-out, retain the existing Attendance_Record unchanged, and return an error message indicating the End_Code is invalid.
8. IF a Student submits a matching End_Code but no check-in time is recorded for that Student, THEN THE System SHALL reject the check-out, retain any existing Attendance_Record unchanged, and return an error message indicating that no check-in exists.
9. WHEN a check-out time is recorded, THE System SHALL calculate the working hours as the difference between the check-out time and the check-in time, expressed in hours rounded to 2 decimal places, and store the value in the Attendance_Record.
10. THE System SHALL store each Attendance_Record in the attendance collection in Cloud Firestore.

### Requirement 11: Estimated Earnings

**User Story:** As a Student, I want to see my estimated earnings, so that I can track the value of my completed work without real payments.

#### Acceptance Criteria

1. WHEN a Student's Attendance_Record for an Event becomes completed by having both a check-in time and a check-out time recorded, THE System SHALL add the Event's Pay_Per_Head exactly once to the Student's Estimated_Earnings total.
2. IF a Student's Attendance_Record for an Event has already been added to the Student's Estimated_Earnings total, THEN THE System SHALL NOT add that Event's Pay_Per_Head to the Estimated_Earnings total again.
3. WHEN a Student opens earnings, THE System SHALL display the Student's Estimated_Earnings total as a monetary amount.
4. WHEN a Student opens earnings, THE System SHALL display the Pay_Per_Head amount credited for each Event for which the Student has a completed Attendance_Record.
5. IF a Student opens earnings and has no completed Attendance_Records, THEN THE System SHALL display an Estimated_Earnings total of 0 and an empty list of per-Event earnings.
6. THE System SHALL exclude wallet features, withdrawals, and payment processing from earnings handling.

### Requirement 12: Reports

**User Story:** As a Student or Vendor, I want to report issues, so that the Admin can review and address platform problems.

#### Acceptance Criteria

1. WHEN a Student submits a Report with a non-empty description and a category of Fake Event or Vendor Issue, THE System SHALL record the Report with the submitting user's identity, the selected category, the description, and a creation timestamp.
2. WHEN a Vendor submits a Report with a non-empty description and a category of No Show or Misbehavior, THE System SHALL record the Report with the submitting user's identity, the selected category, the description, and a creation timestamp.
3. IF a user submits a Report with a missing category or a category not permitted for the user's role, THEN THE System SHALL reject the submission and return an error indication identifying the invalid category.
4. IF a user submits a Report with an empty description or a description longer than 1000 characters, THEN THE System SHALL reject the submission and return an error indication identifying the invalid description.
5. THE System SHALL store each Report in the reports collection in Cloud Firestore.
6. WHEN an Admin opens a Report, THE System SHALL display the Report's category, description, submitting user identity, and creation timestamp for review.

### Requirement 13: Push Notifications

**User Story:** As a user, I want to receive push notifications about relevant events, so that I stay informed of important activity.

#### Acceptance Criteria

1. WHEN an Application status changes to Approved, THE System SHALL send an Application Approved Notification to the applicant Student within 30 seconds of the status change.
2. WHEN an Application status changes to Rejected, THE System SHALL send an Application Rejected Notification to the applicant Student within 30 seconds of the status change.
3. WHEN an Event reminder becomes due, defined as 24 hours before the Event start time, THE System SHALL send an Event Reminder Notification to each Student with an Approved Application for that Event.
4. WHEN a Student applies to an Event, THE System SHALL send a New Application Notification to the Vendor that created the Event within 30 seconds of the application submission.
5. THE System SHALL deliver Notifications through Firebase Cloud Messaging.
6. IF a Notification delivery through Firebase Cloud Messaging fails, THEN THE System SHALL retry delivery up to 3 times with an interval of at least 60 seconds between attempts.
7. IF the intended recipient has no registered device token, THEN THE System SHALL skip delivery for that recipient and record a delivery-skipped outcome without raising an error.
8. IF all retry attempts for a Notification fail, THEN THE System SHALL record a delivery-failed outcome for that Notification and preserve the triggering event data.

### Requirement 14: Data Persistence

**User Story:** As a platform operator, I want platform data stored in defined Firestore collections, so that data is organized and retrievable.

#### Acceptance Criteria

1. WHEN user account data is created or updated, THE System SHALL persist the user account data to the users collection in Cloud Firestore within 3 seconds.
2. WHEN Student_Profile data is created or updated, THE System SHALL persist the Student_Profile data to the students collection in Cloud Firestore within 3 seconds.
3. WHEN Vendor_Profile data is created or updated, THE System SHALL persist the Vendor_Profile data to the vendors collection in Cloud Firestore within 3 seconds.
4. WHEN Estimated_Earnings data is created or updated, THE System SHALL persist the Estimated_Earnings data to the earnings collection in Cloud Firestore within 3 seconds.
5. WHEN Notification data is created, THE System SHALL persist the Notification data to the notifications collection in Cloud Firestore within 3 seconds.
6. IF a write operation to a Cloud Firestore collection fails, THEN THE System SHALL retry the write operation up to 3 times, and if all 3 retries fail, THE System SHALL return an error indication to the caller and commit no partial data for that operation.
